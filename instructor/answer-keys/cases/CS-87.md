# Answer key — CS-87 · Phase-gated agile at program scale

> **INSTRUCTOR ONLY — not published to the site.**

**Model answer:** Two-gate program frame

## Reasoning

Cadence stack: team sprints (existing) → SoS twice weekly (CS-33's design, now 6 teams: 20 min, leads only, dependency output) → monthly program sync (60 min, cross-team replanning, increment health) → quarterly PI planning (2 days, commitment, the two gates scheduled inside). Gates: architecture review before increment 2 of each PI — entry evidence: interface contracts for cross-team integrations and the platform capacity allocation (CS-33's 60/30/10 made contractual); integration readiness before the last increment — entry evidence: nightly cross-team integration green for two weeks and rollback evidence per team. Failure handling: a gate failure does not stop the increment — it converts the affected integration into the next increment's top dependency with named owners; stopping six teams for one failed contract is the failure mode gates must not create. Dependency management: the SoS dependency board scales — requester, provider, need-by, owner — reviewed at every SoS, aged items escalate to the monthly sync. Lightweight list: no portfolio kanban, no lean budgeting ceremony, no additional roles — the design's discipline is what it refuses: every added artifact must name the decision it enables, or it does not enter.

## Alternatives and evaluation criteria

- Full SAFe adoption: defensible when organizational alignment demands the vocabulary; the failure modes named here (six-team integration, platform capacity) need the mechanisms, not the framework's name.
## Facilitation

Ask which gate would have prevented CS-53's fast-tracking disaster — architecture review, with interface contracts as evidence. That is why the gate exists.
